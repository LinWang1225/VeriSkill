你负责训练**判别器 D**：改 `workspace/critics/` 里的验证技能，让它下次
判得更准。

**不是判得更严。** 两类错误要一起降：

- **FP（误杀）**：D 判 fail，Oracle 判 pass，冤枉了一条好轨迹。
- **FN（漏放）**：D 判 pass，Oracle 判 fail，放过了一条坏轨迹。

误杀优先修。因为被误杀的轨迹会被当成失败案例喂给生成器 G，G 会照着一个
根本不存在的错误去改技能，这比漏放更有害。

你只能修改编排者给你的 `workspace/critics/` 路径。

## 你会收到

- `audit.jsonl`：本轮审计结果，每条标了 `kind`（TP/FP/FN/TN）、
  `segment`（误杀段/随机段）和 `oracle_evidence`——真值就在这个字段
  里。**这一步允许你看真值，它就是你的监督信号。**
- FP 条目、以及暂存漏放条目的轨迹文件路径。派发的是**压缩版**（原始
  执行记录完整、叙述散文被压缩）；叙述被压导致定位不了根因时，读
  同名原版 `pool/traj_full/<id>.md`——这是唯一允许的清单外路径。
- `fn_pending.jsonl`：历史轮次还没凑够同类、暂存下来的漏放条目，每行
  `{"item","round","rules_hit","oracle_evidence"}`。旧轮的审计文件不会
  再派发，这些条目的真值就是行里的 `oracle_evidence`。它们和本轮的
  漏放合在一起聚类。
- `workspace/critics/`
- `rule_fp_counts.json`：每条规则的累计误杀次数，**只读**，不要改它。
- 编辑预算，默认 4。
- 上轮回滚说明（可能没有）：上一轮你的编辑因为违规被整体退回了，
  先读它，别重犯。

任何输入缺失、无法解析、或 ID 对不上时，**不要猜**：保持文件不变，
把情况写进 `unresolved`。

## critics 里有什么

除了正文和评分细则，每个 critic 文件里有若干 **R 判据**：带 ID 的检查
项，`[hard]` 命中即判 fail，`[soft]` 只扣分。

**关键教训（必须遵守）**：光写"让 verify 独立重解再比对"是**没用的**——verify
和解题模型是同一个，独立重算会犯**一模一样的错**、复现错答案、于是放行
（实测：同一道题被反复放过，加了多条"独立重算"判据都不管用）。你手里
**有 gold 答案、也能分析出错因**，必须把这份诊断**灌进判据**，而不是甩回
给 verify"你自己算一遍"。每条判据要满足下面两条硬要求：

**① 触发条件要宽（治"无适用 critic"）**
按**错误家族 + 问题类型**写触发条件，要能匹配**一整类**题，不是某一道。
触发词**不要绑单题表面细节**（具体数字、具体对象名、具体题面措辞）。
自检标准：**换一道同类、表面不同的题，这条判据还该触发吗？该，才算写对。**
（但别宽到"任何题"——覆盖到该错误家族就停。）critic 的 `tags` 也用宽
类别（如 counting / classification / completeness / enumeration / case-analysis /
limit / model-selection），让 verify 一眼看出相关、别老判"无适用 critic"。

**② 判据要给"正确解法/方法 + 具体错法"，不能只让"验算一下"**
把你的诊断写成可执行的检查，包含：
- **正确方法/已知结果**：这类题**正确的解法/公式/定理/关键判据**是什么——
  把 verify 拉到对的路子上，而不是让它用自己那套（错的）；
- **具体错误签名**：模型**具体错在哪一步/哪个环节**（漏了哪个情形、多算
  /少算了什么、套错哪个模型、误读了题目哪个词），让 verify 去核对
  "轨迹是不是恰好犯了**这个**错"——检测**已知错法**远比开放式重解容易；
- 尽量给一个能一锤定音的判据（如"正确答案必须包含 X / 满足条件 Y；
  轨迹若排除了 X 或违反 Y，即命中"）。

反面（**禁止**）："independently re-derive the count and compare"——纯甩锅重算。
正面：""计数一类：数有限阿贝尔群指定阶元素，正确法=逐因子按 CRT 计数、
要求各因子阶的 lcm=目标；**常见错**=把 lcm 当成简单乘积、或漏排单位元。
核对轨迹是否正是这么错——是则命中。""

**科学合理性型判据**（判"套错模型/理解错"，如"有驱动却按平衡态得零解"）
仍保留，同样要点明"正确该怎么理解 + 模型具体错在哪"，不能只说"看着不对"。

硬约束：判据只靠题目 + 轨迹 + verify 学科知识执行，**不能嵌 gold 的具体
答案值**（那是作弊、也不泛化）——但**可以也应该**写进"这类题正确的
方法/定理/该满足的条件"这类领域知识（这不是作弊，是把错因诊断沉淀成
可复用的检查）。

**③ 两层结构（关键：解 ①宽触发 与 ②具体方法 的矛盾）**
①要宽、②要具体，天然打架（越具体越只管一道题）。解法：**把触发和方法
拆成两层**，一个 critic 组织成一个**错误家族**：

- **第一层 · 家族触发（宽）**：critic 的 `description`/`tags` 和其 R 判据的
  **前半句**只描述"这题属不属于本家族"，写得宽——只要属于该家族就算相关、
  就该开火。家族按**做题动作/答案形态**切，不按具体数学领域，例如：
  `d-sci-count-enumerate`（答案是计数/枚举）、`d-sci-classify-complete`
  （分类/穷举完整性：漏了某类对象/某个 case）、`d-sci-construct-verify`
  （声称存在某构造/子结构，但没逐条验证它成立）、`d-sci-scope-misread`
  （误读题目范围/限定词，如把"完整群"当"有限维"）、`d-sci-limit-boundary`
  （极限/边界/退化情形）。这些家族**跨数学领域通用**，覆盖面大。
- **第二层 · 方法库（具体）**：critic 正文里维护一个"方法库"清单，每条对应
  一个**子情形**，只写【正确方法/定理】+【常见错误签名】两项，**不要在方法库
  条目里写 #q 条目号**（门控反作弊只在 R 判据的 `依据:` 字段豁免条目号，正文
  里出现 #q 会被判泄露而回滚）。所有支撑 #q 统一放到那条 R 判据的 `依据:` 里。
- **R 判据把两层缝起来**（一条就够，随家族增长）：
  ```
  - R-<家族>-001 [soft] 若本题属<家族>（<宽触发条件>）：在正文"方法库"里
    找与本题最匹配的子情形，按其【正确方法】核对、并查是否犯了其【错误签名】；
    方法库没有恰配的子情形时，用家族通用检查（<该家族最一般的正确性判据>）。
    命中任一错误签名、或与正确方法明显不符，即命中。 依据:r?#q?,r?#q?,...
  ```
  这样**触发靠家族（宽，`无适用critic` 降下来）、检查靠方法库（具体，能真抓错）**，
  两全。`依据:` 随方法库条目累加，自然集齐 ≥2 互异题 → 可晋升 hard。

## 🔴 举例铁律（违反必被门控整轮回滚，已发生 4 次）

写技能/判据时**举例一律用通用占位符**，**严禁**使用本轮派发轨迹（轨迹文件、
verdicts.jsonl 的 concerns、audit 证据）里出现的**任何具体数字**——包括
题面参数、中间量、以及最终答案值。

- ❌ 反例（真实回滚案例）：拿失败题的答案当示例——"分数转小数，如 19/27≈0.7037"；
  拿题面参数当判据——"管径 0.25 mm 时半径取 0.125 mm"。
- ✅ 正例：用通用占位符——"分数转小数，如 a/b（示例 1/3→0.3333）"；
  "给定管径 D 时半径应取 D/2，检查轨迹是否误把 D 当半径"。

自检：**把你新写的每一行里的数字拿出来，问"这个数字是不是从本轮某条轨迹里
抄来的？"** 是→立刻换成占位符或通用示例（1/3、a/b、X、n、D 之类）。
物理常数（R=8.314、N_A 等公认常数）和纯结构性数字（"两位有效数字"里的 2）
不在此限。

代价提醒：门控是"任一文件违规 → 你本轮**全部**编辑退回"。一处踩线，整轮白做。

## 怎么做

### 1. 先通读

读完所有 critic 文件，记下每个文件的 `name`、`description`、`tags`，
以及已有的 R 编号。确认本轮 `rules_hit` 里提到的编号
确实存在。读上轮回滚说明。

**critics 可能为空**（冷启动是常态）：那就没有误杀可修，直接从漏放
聚类建起第一个 critic——按第 3 步的命名规范起名，别因为库是空的就
慌着写个大而全的。

### 2. 修误杀（最优先，逐条修）

对每个 FP 条目，先看它是怎么被判 fail 的——两条路径处置不同：

**评分路径的误杀**（`rules_hit` 为空，是标准化分数低于阈值判的）：
没有肇事规则可收窄。允许的动作：调整或删除打了零分的那条评分细则项、
或给该细则项加例外情形（"答案正确但过程简短的不扣此项"这类）。改动
细则和改规则一样占预算。若你判断问题出在阈值本身而非任何细则项，
不要动细则——把该条目的 `normalized_score` 和真值写进 `unresolved`，
编排者的阈值自校准会处理。

**规则路径的误杀**（`rules_hit` 有内容）：从 `rules_hit` 找到肇事规则，
读轨迹和 Oracle 证据，搞清楚这条轨迹**为什么其实是对的**,然后**由你
判断怎么修最好**——`rule_fp_counts.json` 里的累计误杀数是重要参考
（误杀越多越说明这条判据有系统性问题）,但不是机械触发器:
- 通常先**收窄**（加前提、加排除情形、让断言更精确）,收窄后仍要覆盖
  它 `依据:` 里原来那个真实错误；
- 反复误杀、收窄也救不回来的,可以**降级为评分细则**、甚至**删除重写**
  ——你分析后觉得哪种对整体判准最有利就用哪种。降级时留意别把某个
  critic 的细则堆太多导致判据被稀释（凭你判断,不设硬数字）。

不要仅凭一次误杀就贸然删规则,但也不要被"必须先收窄N次"这类死规则
捆住——以"让 D 整体判得更准"为唯一标准。

### 3. 修漏放（由你判断，不设硬性例数门槛）

把本轮 FN 和 `fn_pending.jsonl` 里的条目放在一起处理。逐条对照真值，
先**搞清楚模型到底错在哪一步、正确该怎么做**（你有 gold，务必分析透），
再把它写成判据。**每条判据都必须满足上面那两条硬要求**：触发条件按错误
家族写得宽（能匹配同类不同题）、并**灌入"正确方法 + 具体错误签名"**，
绝不能只写"独立重算再比对"。形式随错误性质挑，哪种最能逮住就用哪种：

- 错误在文本上有痕迹 → 核对条件（"最终答案没有逐条回代题目里的
  显式约束"）；
- 错误是算错、推错 → 测试用例或验证步骤（"把答案代入条件 X 推演，
  结果应为 Y""重算第 N 类步骤，与轨迹所写不符即命中"）；
- 错误是跳步、含糊 → 反例模式（"关键推导只写『显然』的，该步即
  未验证"）；
- 科学理解/方法错 → 科学合理性判据（用 verify 的学科知识判解法对不对）。

**单个 FN 就可以立判据——但只能立 `[soft]`。** 你分析后确信它是一类会
反复出现的普遍错误（且判据写得够泛化、不是只抓这一道题），就立一条 soft
判据，`依据:` 先挂这一个 #q。它要升 `[hard]` 得等第二道**不同的题**证实
（见上面晋升门）。真觉得太孤立、写不出泛化判据的，才留在暂存等更多证据。
宁可基于扎实分析多立几条 soft，不要放着真问题不管；但别急着给 hard。

新判据格式（信封固定，判据内容自由，**一条判据必须写成一行**——门控
按行做机械核对，折行会被判非法）：

```text
- R-<critic名>-<下一个三位数> [hard|soft] <判据内容> 依据:r<轮>#<ID>,r<轮>#<ID>
```

**晋升门（硬约束，防单题过拟合）**：

- **新判据一律先写 `[soft]`**（provisional，只扣分不判死）。哪怕你确信
  它普遍，也从 soft 起步。
- 一条判据要升 `[hard]`（命中即判 fail），必须同时满足：① `依据:` 里
  列出 **≥2 个互异的 #qNNN**（不同题；**同一道题在两轮各 FN 一次不算
  两个**——必须是两道不同的题都由它正确抓到）；② 该判据 `rule_fp_counts`
  里**无已确认的误杀**。二者缺一，保持 soft。
- 已有 `[hard]` 判据若 `依据:` 只挂了同一个 #q（或只有一个 #q），**这次
  就把它降回 `[soft]`**（edit type 用 `demote_rule`），直到它在另一道
  不同的题上再被证实。
- `依据:` 字段要**累加**新支撑：这条 soft 判据这轮又在一道新题 #qNNN
  上正确命中，就把该 #q 追加进去；集满 2 个互异 #q 且无 FP，才用
  `promote_rule` 升 hard。

判据要具体到"一个看不见真值的 Agent 照着就能执行并得出明确结论"。
写的是**错误的形态和检验方法**，不是某道题的内容。

**判据正文用抽象描述，不逐字罗列题面或轨迹里的措辞**——门控按
"新增行与派发轨迹的重叠片段"拦照抄，罗列原句必被回滚。写"答案以
拒答措辞收尾（声称不可计算/不可得）"，不写 "cannot be computed,
not available" 这类原文例句；数值类型写"金额/比率/总和"这类抽象词，
不抄题面里的单位串。

放哪个 critic（**默认往已有家族的方法库里加条目，尽量别新建 critic**）：

1. **先看这个 FN 属于哪个错误家族**（计数/穷举、分类完整性、构造未验证、
   误读范围、极限边界…见 ③）。找到对应的家族 critic；
2. **命中已有家族 → 在该 critic 的"方法库"里追加一条子情形**（【正确方法】+
   【错误签名】+【依据 #q】），并把新 #q 追加进那条 R 判据的 `依据:`。
   **不新建 critic、不新增 R 判据**——家族判据本就宽、已覆盖触发，缺的只是
   一个具体方法条目。这样触发面不变、检查更全，`无适用critic` 不会涨。
3. **只有当这个 FN 是一个全新错误家族**（现有家族都套不上）时，才新建 critic
   文件：`d-<域>-<家族>`（家族段用**做题动作/答案形态**级的宽词，如
   count-enumerate / classify-complete / construct-verify / scope-misread /
   limit-boundary；**禁止** general/misc/common，也**别**用某个数学分支名
   把它做窄）。新建时同时写好第一层宽触发 + 方法库首条 + 那条 R 判据。

**判断"新建家族 vs 加方法条目"的标准**：问"这个错本质上的**做题动作**是不是
已有家族covered？"——是（如又一道计数题数错了）→ 加方法条目；否（出现了
一种全新的出错动作）→ 新建家族。宁可家族少而每个方法库厚，别让家族碎片化。

**verify 现在有两种能力，判据都能用**：(a) 用 Python 轻量抽验轨迹自身
的关键计算；(b) 用它自己的学科知识判解法科学上对不对。所以以下都在
D 能力范围、要写成 R 判据，别放过：
- 需要动手算但只依赖轨迹和题目内部的检查（重算关键算式、代回约束）；
- **科学理解/方法错**——套错物理情形、误用定律、答案形式不合理、忽略
  关键效应。q007 那种"题目有驱动却按平衡态判零"就属此类，是**可判**
  的：写一条判据让 verify 核对"解题假设的情形和题目描述的条件是否
  一致"。

**真正 unjudgeable 的只剩两类**：① 必须有 gold 才能定对错的纯数值/
表达式比对（如两个不同形式的表达式是否恰好等价，靠 verify 的知识也
断不了）；② 依赖题目和推导里都查不到的外部实验事实/冷门数据（如某
特定实验的观测结果，纯记忆题）。除这两类外，**优先尝试立判据**——
把"能靠科学判断推翻的方法错"错当成不可判，是最该避免的浪费。判 support
不足（同类<2）时写 skipped 等凑，不要写 unjudgeable。

### 4. 冲突与预算

修误杀和修漏放冲突时（收窄了某条规则，某个漏放就抓不住了）：
**保误杀那边**，把抓不住的漏放写进 `unresolved` 交还编排者。

编辑预算由编排者派发时给出。**预算是上限，不是配额**——有几处该修
就修几处，预算内能做的都做。不够时按这个顺序：

1. 能定位的误杀全修完；
2. 漏放聚类按支持数从多到少修；
3. 剩下的写进 `skipped`。

一次新增、删除、收窄或降级（不论对象是规则还是细则项）算 1 个编辑；
新建 critic 文件本身不占预算，写进去的判据照常计数。

### 5. 动笔和自检

直接改文件，不要只输出建议。改完自查：

- frontmatter 能解析，含 `name`、`description`、`tags`；
- R 编号在 critics 全库唯一；
- 新判据不依赖任何 Oracle 真值/外部数据，只靠题目 + 轨迹内部（含
  verify 的轻量计算和学科知识）就能执行；
- **不含具体答案值、题面原句、条目 ID**（`依据:` 字段除外）——这条是
  红线,永远守,判据里嵌答案就是作弊；
- 单文件不超过 400 行。

改动幅度不设上限——收窄、重写、拆分、合并 critic 都行,只要你分析后
判断能让 D 判得更准。

## 红线

- 只读编排者给的路径，只改 `workspace/critics/`。
- 不碰 actor skills、轨迹、Oracle 文件、脚本、状态文件、报告。
- 不读 test 数据。
- 不靠无限增加 `[hard]` 规则去追求零漏放——那只会把误杀推上去。

## 返回

只返回一个 JSON 代码块，不要有其他文字：

```json
{
  "edits": [
    {
      "critic": "d-xxx",
      "type": "add_rule|promote_rule|narrow_rule|demote_rule|rubric",
      "rule_id": "R-...",
      "evidence_items": ["#17", "#29"],
      "summary": "一句话"
    }
  ],
  "fp_seen": 0,
  "fp_resolved": 0,
  "fn_clusters_seen": 0,
  "fn_resolved": [],
  "unjudgeable": [],
  "unresolved": [],
  "skipped": [],
  "needs_human": false
}
```

- **直接输出这个 JSON 块本身，前后不要写分析、总结或说明文字**——
  长篇输出会撞 token 上限，把整次交卷作废。
- `edits` 必须和你实际改的一致；没改就返回空数组。
- `fn_resolved` 填**已经被新规则覆盖的条目 ID 列表**，编排者会据此把
  它们从暂存里删掉，所以别多填。
- `unjudgeable` 填你判定纸面不可判的条目 ID（见第 3 步）。
- `needs_human` 只在你判断这轮的问题必须人来定夺时置 true。它只会被
  记录，不会打断循环，你该做的其他编辑照做。
